# 附件同步冲突

附件基准包含服务端版本标识和完整 SHA-256，只在上传得到匹配的确认、下载完成，或服务端核对两端完整内容一致后记录。旧的 `baseHash` 是采样哈希，不用于单独判定两个附件版本是否一致。旧的 SHA-only 基准或丢失的版本标识按未知版本处理，不会根据时间或采样哈希猜测；需要重新同步以取得可验证的版本。

多个设备从同一基准修改附件时，服务端在最终写入前比较当前完整 SHA-256。第一个成功提交的版本保留在原路径；基准已经改变时，服务端会把远端和本次提交的版本分别保存为同目录的 `名称.conflict-remote-标识.扩展名` 和 `名称.conflict-incoming-标识.扩展名`，并在同步日志中报告。即使随后选择保留本地版本，原远端版本仍有独立副本。收到远端版本时，插件也会保护尚未同步的本地修改，并将不同的远端内容保存到同目录的冲突副本。

在 Obsidian 中打开发生冲突的附件，可运行命令「解决当前附件冲突：保留本地版本」。确认后，插件会以冲突时记录的远端 SHA 提交本地版本；如果远端再次变化，服务端会继续保留冲突，不会盲目覆盖。也可检查冲突副本后手动整理文件。远端删除与本地修改冲突时，插件保留本地文件并记录日志；此情形目前不能通过该命令自动恢复到远端。

收到远端重命名时，如果本地目标路径已经有附件，插件会保留本地文件，并重新获取远端内容进行完整 SHA-256 比较；内容不同时将远端内容保存为冲突副本。获取失败后，打开目标附件并运行上述命令，可以重新请求验证。正常重命名也会重新核对远端版本，避免把本地编辑误记为已同步。

附件上传、删除、重命名，以及启用离线删除同步时积累的删除，会提交最后确认的版本标识和完整 SHA-256。即使远端删除后以相同字节恢复，版本也会变化，旧操作不能把它当成原版本。基准未知或远端已变化时，服务端会保留冲突。插件会阻止后续扫描重复提交旧操作；可以取得远端版本时，会保留不同的本地内容并保存远端冲突副本，本地文件不存在时则恢复远端文件。离线删除逐条等待服务端确认，单次操作使用独立标识关联回执。

对于删除或重命名冲突，在原路径打开已取得的远端附件后，也可运行「解决当前附件冲突：保留本地版本」。此时确认对话框会说明实际操作是保留远端版本并放弃旧的删除或重命名：插件只有在本地文件的完整 SHA 与冲突记录中的远端 SHA 一致时才解除冲突，不会向服务端写入文件。路径哈希不匹配、重命名目标已存在、远端已删除，以及无法取得可验证远端版本的情况需要结合日志和本地文件人工处理。

如果获取远端版本失败，可以在同步完成后运行「重试获取冲突附件的远端版本」，输入同步日志中的原始附件路径。本地附件已经删除时也可以使用；插件会先检查冲突记录、仓库和连接状态。无法验证远端版本的冲突需要人工检查。

先升级同步服务，再升级所有使用该仓库的插件。新插件连接未声明附件版本能力的服务时会暂停附件同步，并将该轮标记为部分完成；笔记、文件夹和配置仍可同步。旧插件、没有提交版本基准的客户端和旧接口仍按兼容行为工作，不受新版本校验保护。Windows 服务端尚未实现新日志的恢复，暂不声明该能力。

多个服务进程必须共享同一份数据库和 `storage/` 卷，并使用支持可靠文件锁、硬链接、原子重命名与 fsync 的文件系统。所有实例都需升级；不同本地卷、外部程序直接修改文件和不可靠的网络文件系统不在保护范围内。服务进程中途退出后，存活或重启的实例会在访问附件前恢复未完成的上传和重命名日志。旧存储路径的附件仍可读取、删除和恢复；覆盖及重命名在安全迁移前会拒绝，并需人工处理。

服务端若因数据库或磁盘错误无法创建冲突副本，会报告失败并尝试把已校验的上传快照移到配置的临时目录同级的 `<temp-path>-conflict-recovery/<session-id>/snapshot`，实际路径写入服务日志。该目录不属于常规临时文件清理范围；如转移本身失败，应在重启服务前根据日志保存仍在临时目录的快照。
