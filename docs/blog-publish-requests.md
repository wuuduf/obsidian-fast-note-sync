# 博客发布请求恢复

当前笔记发布和“重试当前笔记博客发布”共用同一请求保护：相同 API、笔记库和笔记范围在请求未结束时只发送一次，成功或失败后都释放保护，允许下一次明确操作。不同笔记范围仍可分别提交。

发布请求等待上限为 30 秒，fetch 和 Obsidian requestUrl 两种网络模式均有回归覆盖。等待超时不代表服务端取消发布任务；插件会提示“任务可能已排队，请先检查发布历史”，避免误以为从未入队而反复提交。

WebGUI 的发布历史提供“重新检查并发布”：服务端按原保存范围检查后重试，并回写重试中、已恢复或再次失败；旧历史没有保存发布范围时，需要通过目标的发布检查重新发起，不能把原单篇任务悄悄改为全量发布。服务端操作说明见生态中的同步服务 runbook。

HTTP 请求绑定发起时的 API、运行时地址、账号凭据、笔记库、网络模式和重定向白名单。请求期间切换这些连接设置后，旧响应会被拒绝，不会把新连接地址改回旧服务，也不会把旧账号数据显示为新连接的结果。需要在新连接重新发起操作；对发布请求，这仍不代表旧服务已经取消排队任务。

已取消的请求不会开始网络工作。Obsidian `requestUrl` 的取消只能停止等待，无法中止其底层网络传输；插件会忽略晚到结果，并在成功、失败或取消后移除取消监听器，避免反复请求积累监听器。

每个 HTTP 逻辑请求携带独立的 `X-Trace-ID`。发布成功、应用错误和等待超时提示都保留诊断 ID；服务端返回的有效响应 ID 优先于本地发送 ID。可用此 ID 对照服务端持久化任务、发布历史和历史重试，历史重试沿用原任务的根 ID。并发请求各自保存 ID，不依赖全局“最后一个请求 ID”。
